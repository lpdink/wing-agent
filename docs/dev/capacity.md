# 容量与并发上限（capacity）

网关能扛住多少**并发活跃会话**、在哪个点退化、退化在内存还是速度上——这份文档给出测量方法、实测数字与结论。
工具在 `scripts/capacity/`（手工、可复现、不进 CI 门禁）；它测的是**网关自身**的开销，不是模型的快慢。

> 本文所有数字来自一次完整测量：Apple Silicon / 12 核 / 16 GB / macOS（APFS）/ `wing` `0.7.0`（commit `a7e7126`，
> 即在 `develop` 上与本工具同批）。**换机器数字会变**，方法与判据不变。

## 1. 结论

**三个数就够了：**

| 问题 | 答案 |
|---|---|
| 出厂默认能同时跑几个在生成的会话？ | **100**。第 101 个开始排队，症状是**卡 300 秒后按首块超时失败并重试**（不是变慢） |
| 打开连接池后，单进程能跑几个满速会话？ | **约 200 稳定**（p99 21 ms）；400 已到 1 核边缘（p99 166 ms）；700 以上**崩塌** |
| 1000 个会话**同时活着**行不行？ | **行，但每会话速率要压到 ≤10 事件/s**（p99 207 ms）；5 事件/s 舒适（p99 111 ms / 0.47 核） |

**内存不是瓶颈**：空转会话 ~17 KB/个，1000 个约 83 MB。真正的内存风险在**过载**：积压会把 RSS 顶到 800 MB 以上（见 §4）。

## 2. 口径：三种「并发」别混

- **事件（event）** = 上游一个 SSE delta 帧 = 网关一次 `emit` = 一条出网 WS 帧。负载强度的基本单位是**事件/s**，
  不是 token/s。`--rate` 是**每会话事件/s**；`--chunk` 是每事件字符数（默认 1 = 最坏情况）。
- **会话（session）** = 一个可被驱动的上下文。它的成本由两件正交的事组成：
  **事件成本**（∝ 每秒帧数）与**轮次固定成本**（∝ 每秒轮次数），见 §5。
- **两种读数都不能外推**（测量时踩过）：
  - 单连接、低速率（N=1）的「每事件成本」含**刚睡醒的冷启动开销**，不能外推到多并发；
  - 单连接、高速率（如 10k 事件/s）会把「一次唤醒吃多帧」的红利算进去，不能外推到多连接
    （1000 条连接时 `reads/event ≈ 0.98`，几乎没有批量）。

## 3. 结构墙：三个「不是 CPU 的上限」

按咬人的先后排序。前两条与代码位置绑死，改配置即可跨过；第三条是架构性的。

### 3.1 provider 连接池 = 100（出厂默认，最咬人）

`httpx.AsyncClient` 未显式传 `limits` 时用默认池（`max_connections=100`），而 provider 实例是**全进程共享**的
（每个配置条目一个实例、一个 client）。SSE 是长连接，所以：

> **同一个 provider 上并发超过 100 个调用，第 101 个在本地连接池排队。**

排队发生在 `send(stream=True)` 内部，而它被 `wait_for(timeout_first_chunk)`（默认 **300 s**）包住。
所以用户看到的不是「变慢」，而是**卡 5 分钟后按首块超时失败**，再按 `max_retries`（默认 10）重试——
雪崩式的重试。**这是正确性问题，不是性能问题。**

- 修法：`providers[].max_connections: 2000`（见 `docs/dev/settings.md`）。
- 实测证据：同一个 1000 会话负载，池不打开时窗口内只产出 **99 503 帧 ≈ 99.5 个会话**的满速输出
  （其余 900 个在排队）；打开后线性恢复到 10 倍。

### 3.2 文件描述符

N 个会话 × 每会话一条 WS + 一条上游 SSE ⇒ ≥ 2N 个 fd。本机 `ulimit -n` 软限 **256**（硬限 unlimited），
1000 会话直接 `EMFILE`。容量工具自己会 `setrlimit` 并把生效值写进报告（`host.ulimit_n`）；
**部署侧必须自己抬**（systemd `LimitNOFILE=` / shell `ulimit -n`），量级取 `4×目标会话数 + 256`。

### 3.3 单进程事件循环 = 1 核

网关是单进程 asyncio（全库没有并发上限/no worker 池），所以硬顶是一个核的 CPU 预算。§4 的曲线就是这条线的形状。

## 4. 速度轴：实测曲线

负载：`pure_stream`（每会话一条持续流），`--rate 50 --chunk 1`，池 `max_connections: 2000`，每档 15 s 采样窗口。

| 会话数 | 实测事件/s | 网关 CPU | 投递 p99 | 网关 RSS |
|---|---|---|---|---|
| 100 | 4 939 | 0.39 核 | 9.5 ms | 93 MB |
| 200 | 9 866 | 0.46 核 | 21 ms | 112 MB |
| 400 | **19 587** | **1.00 核** | 166 ms | 158 MB |
| 700 | 7 958 | 1.00 核 | **10.3 s** | 588 MB |
| 1000 | 1 394 | 1.00 核 | 6.1 s | **817 MB** |

**读法**：

- **线性区到 200 会话**（p99 21 ms 以内，仍在人的无感区内）；
- **400 会话到 1 核**，这是单进程的**吞吐峰值 ≈ 2 万事件/s**；p99 已经 166 ms（可感，但不算坏）；
- **700 以上崩塌**：吞吐**下降**到 8k 再跌到 1.4k，p99 数秒，RSS 随积压膨胀到 800 MB —— 过载不丢负载，
  而是**把积压堆进内存**。这是最危险的一段：看起来"还活着"，实际上内存与延迟同时失控。

### 1000 个会话同时活着：可持续包络

固定 1000 会话，只改每会话速率（同样 15 s 窗口）：

| 每会话事件/s | 实测事件/s | 网关 CPU | 投递 p99 | RSS |
|---|---|---|---|---|
| 50（满速） | 1 394 | 1.00 核 | 6.1 s | 817 MB |
| 20 | 10 601 | 1.00 核 | 8.8 s | 458 MB |
| 15 | 13 633 | 1.00 核 | 2.5 s | 292 MB |
| **10** | 9 909 | 0.94 核 | **207 ms** | 241 MB |
| **5** | 4 964 | 0.47 核 | **111 ms** | 234 MB |

**同样的「2 万事件/s」，用 400 条连接跑是健康的（p99 166 ms），用 1000 条连接跑就崩（p99 2.5 s）** ——
成本随**连接数**增长的部分，不止随事件数。所以容量必须报成 **(会话数, 每会话速率) 的包络**，
报一个「支持 N 并发」的裸数字是误导。

### 单连接的天花板（参考）

一条连接、无 pacing 压力时能到 **10 248 事件/s @ 0.54 核，p99 0.12 ms**。这条曲线**不能**当容量用
（见 §2 的两种不可外推），它的价值是标定「一次唤醒吃多帧」能有多便宜。

## 5. 另外两条轴

### 5.1 轮次固定成本：3.3–4.9 ms/轮

`tool_cycle`（每轮一次工具调用 + 一次 1 字符文本）：

| 形态 | 轮次/s | 网关 CPU | 每轮 | 轮次 p50 |
|---|---|---|---|---|
| N=1，每 3 s 一轮 | 0.33 | 0.01 核 | ~30 ms | 3 022 ms |
| N=100，每 3 s 一轮 | 33.3 | 0.11 核 | 3.3 ms | 3 315 ms |
| N=100，每 0.2 s 一轮 | 157 | 0.72 核 | 4.6 ms | 628 ms |
| 同上但工具用 `Bash`（子进程） | 154 | 0.76 核 | 4.9 ms | 631 ms |

- 1 核 ≈ **200–300 轮/s**；**子进程工具只多 0.3 ms/轮**（工具本身的成本远小于轮次固定成本）。
- 换算到真实 agent（轮长 4–40 s）：1000 个会话 = 25–250 轮/s = **0.1–1.1 核**。
  也就是说**轮次频率**与**事件速率**是两条独立的预算线，谁先撞上取决于模型多快、工具多久。
- 每轮固定成本的构成：上下文装配 + 整段会话序列化 + `history.jsonl` 的 append+fsync + 审计 INSERT。
  它**随文件系统变**（APFS 的 fsync 比 ext4/NVMe 贵一个量级），所以这条数字只能同机比较。

### 5.2 内存：空转 17 KB/会话，过载才是杀手

| 场景 | 网关 RSS |
|---|---|
| 空载基线 | 64.5 MB |
| 1000 个空转会话 | 82.6 MB（≈ +17 KB/会话） |
| 1000 个会话 × 50 事件/s（过载） | **817 MB** |

- **会话本身很便宜**（元数据 + 惰性水合的链）；1000 个空转会话是 16 GB 的 0.5%。
- 过载时增长的是**积压**（读进来还没处理完的帧），不是会话状态。它没有上界——
  这是「1000 全集满速」最危险的后果。
- 未测：历史体量极大的会话（几 MB/会话的链）会改变空转的斜率；媒体/图片同理。见 §8。

### 5.3 水合尖峰

100 个会话（每个 2 000 token 历史）重启网关后同时 subscribe：`sync_session` p99 **43.5 ms**、
首帧 p99 164 ms、网关 0.02 核。**不是瓶颈**。

## 6. 为什么是这个形状（成本归因）

1. **每事件成本随速率下降 8 倍**（单连接：518 事件/s 时 297 µs/事件，10 248 事件/s 时 52 µs/事件）
   ⇒ 大头不是解析/序列化，而是**每次唤醒的调度开销**；同一条连接上缓冲住的多帧会被一次唤醒批量吃掉。
2. **连接之间不能合并**：1000 条连接时 `reads/event ≈ 0.98`。所以「大批量读上游」只能省掉一小部分
   （实测 ~1.06x）；真正的杠杆是**减少连接到网关的帧数**或**降低每连接的帧率**。
3. **事件通路在目标档的预算**（1000 连接 / 1000 活跃会话，逐项实测相加）：
   读+解析 17.0 µs + **`EventBus` 扇出 28.0 µs** + 对象/序列化 3.4 µs + 出网 4.3 µs ≈ **52.7 µs/事件 ≈ 2.6 核**
   （对应 5 万事件/s）。其中 `EventBus` 的两处 **O(会话数/连接数)** 扫描占了 53%：
   `session → clients` 反查与活跃会话的订阅者解析；索引化后同一预算降到 **1.29 核（2.05x）**。
   **这是下一个可做的优化**（未在本次实施：它需要改事件总线的核心路由结构，应当独立成 PR 并配套
   「每事件成本不随会话数线性增长」的断言）。
4. **过载为什么崩塌而不是排队**：网关既不丢帧也不限流，读得进来就全读进内存；上游因此感受不到背压，
   继续按自己的节奏发。于是队列/内存同时增长，事件循环把时间花在扫描与调度上，实际吞吐反而下降。

## 7. 怎么复现

```bash
# 0) 抬 fd（本机软限只有 256；工具会自己再抬一次并记录生效值）
ulimit -n 8192

# 1) 离线自测（不联网、~35 s，验证编排/采样/配对/判据/报告）
uv run python scripts/capacity/run.py --selftest

# 2) 速度轴阶梯（池必须打开，否则测的是 httpx 默认值）
uv run python scripts/capacity/run.py --scenario pure_stream \
  --levels 100,200,400,700,1000 --rate 50 --chunk 1 \
  --provider-max-connections 2000 --dwell 15 --warmup 5 \
  --out target/capacity/stream

# 3) 1000 会话的可持续包络
for r in 20 10 5; do
  uv run python scripts/capacity/run.py --scenario pure_stream --levels 1000 \
    --rate $r --chunk 1 --provider-max-connections 2000 --dwell 15 --warmup 5 \
    --out target/capacity/n1000-r$r
done

# 4) 内存轴 / 轮次轴 / 水合尖峰
uv run python scripts/capacity/run.py --scenario idle       --levels 1,100,1000 --dwell 15
uv run python scripts/capacity/run.py --scenario tool_cycle --levels 1,100 --cycle-s 3
uv run python scripts/capacity/run.py --scenario tool_cycle --levels 100 --cycle-s 0.2 --tool bash
uv run python scripts/capacity/run.py --scenario hydration  --levels 100 --history-tokens 2000

# 5) 漂移对照：与第 2 步同参数只跑 100 档，偏差 >20% 则整轮作废
```

产物：每档一份 `run.json`（机器读）+ `report.md`（人读，含 `verdict` / `reasons` / 低置信标记）。
判据写死在 `scripts/capacity/verdict.py`（`degraded` / `capped` / `low_confidence` / `unjudged` 四态独立），
报告文案不得出现第二份阈值。

## 8. 已知边界与缺口

- **机器相关**：所有 µs/核数都绑这台机器（尤其 fsync 与 `asyncio.sleep` 的 overshoot ~2 ms，
  后者会让「每帧 sleep」的注入速率系统性偏低——工具会实测 overshoot 并从帧间隔里扣掉）。
- **`--chunk=1` 是最坏情况**：真实 provider 每个 delta 常见 1–20 字符；本机测过 `--chunk 4` 时
  字符吞吐线性 4 倍（1 968 chars/s vs 492），但**事件/s 不变**，而成本由事件/s 决定。
- **未测历史体量对空转内存的影响**：§5.2 的 17 KB/会话是「几乎无历史」的值；几 MB 的链会显著改变斜率。
  媒体/图片未测。
- **未测多进程/多 worker**：结论是单进程的。要把 1000 × 满速做到可用，方向是**多进程 + 前置分流**，
  或者把 §6.3 的 `EventBus` 索引化（2.05x）做掉。
- **不做门禁**：容量数字依赖机器与邻居负载，不进 CI；回归门禁仍由 `scripts/perf/` 的 merge-base 交错 A/B 负责。
- **未覆盖**：`subscribers=per-shard`（一个前端订阅多会话）的形态、远程工具、压缩、媒体上传在容量下的表现。
